## Opening: 30–45 seconds

“I built an airline operations data platform that takes events from Kafka,
retains the original messages in a raw data lake, and transforms them into a
constrained PostgreSQL model with PySpark. The focus is reliable ingestion and
reprocessing: duplicates, out-of-order arrivals, and failed database loads.
The operations console makes the resulting flight state and data quality visible.”

## What data is used?

All flight and passenger data is **synthetic**, generated by the Python simulator
in `airline_ops/producer.py`. There is no commercial airline feed, live flight
tracking API, or real passenger information. Airport codes and routes describe
real US locations; flight numbers, times, gates, delays, and booking IDs are
simulated. The map outline is derived from public-domain Natural Earth boundaries.

Each default simulation generates four flight instances:

| Flight | Route | Final gate | Recorded delay |
| --- | --- | --- | ---: |
| AO100 | JFK → LAX | B10 | 10 minutes |
| AO101 | BOS → ORD | B11 | 15 minutes |
| AO102 | SFO → SEA | B12 | 20 minutes |
| AO103 | ATL → MIA | B13 | 25 minutes |

Each flight has a schedule event, gate change, three passenger check-ins, a delay,
and a departure. That makes 28 unique events. Four deliberate duplicate delay
events make the producer's total 32 messages. Arrival order can be shuffled.

A JSON event includes `schema_version`, `run_id`, `event_id`, `event_type`,
`flight_id`, `flight_number`, `timestamp`, and event-specific values such as
`origin`, `dest`, `scheduled_dep`, `delay_min`, `reason`, `gate`, and `pax_id`.

## Explain the architecture: 60 seconds

- **Python producer → Kafka.** Flight IDs are message keys, keeping each flight's
  messages on a consistent partition. A producer manifest records acknowledged
  offsets only after all messages are delivered.
- **Kafka → Python consumer → MinIO.** The consumer writes the original JSON
  envelope before committing its Kafka offset. Raw object keys include UTC date,
  topic, partition, and offset. Retries use the same deterministic key.
- **MinIO → PySpark.** Completed manifests define bounded batches. Spark reads
  raw JSON via S3A, casts values, handles nulls, rejects invalid records, removes
  duplicates, and determines the final state using event time.
- **PySpark → PostgreSQL.** JDBC loads staging tables. A database transaction
  merges parent and child records while retaining primary, foreign-key, and
  check constraints. Invalid child data rolls back the transaction.
- **Python API → React console.** The local API reads PostgreSQL results and MinIO
  payloads. The public site reads an exported snapshot; it never connects to the laptop.

Kafka ingestion is continuous. Spark transformation is batch-based and needs an
explicit run or scheduler; continuous production alone does not schedule Spark.
MinIO is an S3-compatible local data lake substitute. Azure ADLS provisioning and
`abfss://` authentication are not implemented.

## Data model

The complete column definitions and constraints are in [schema.md](schema.md).

| Table | Purpose and important keys |
| --- | --- |
| `flights` | `flight_id` primary key; route, schedule, actual departure, gate, status; source run reference |
| `delays` | `delay_id` primary key; foreign key to a flight; delay value and observation time |
| `passengers` | Flight-specific `pax_id` primary key; foreign key to a flight; check-in time |
| `pipeline_runs` | Run identity, manifest, counts, transformation status, and timestamps |
| `rejected_events` | Invalid events retained for investigation |
| `data_quality_report` | Actual test outcomes with run and validation IDs |

A flight instance ID includes the service date and run UUID. AO100 can appear in
several independent simulations without violating uniqueness. Replaying an existing
run uses the same identifiers and leaves its normalized records unchanged.

## Show reliability: 45 seconds

Open **Quality** and explain a few actual assertions:

- Kafka delivery offsets and payloads match the consumer's MinIO objects.
- Scoped row counts match four flights, four delay observations, and twelve bookings.
- No orphan records exist; PostgreSQL also rejects an invalid foreign key.
- Negative delays are rejected by database constraints.
- An invalid child load rolls back its parent update.
- Replaying a transformed batch does not change its rows or flight state.

The Quality screen shows the latest integration validation for the selected run.
The repository contains 33 unit tests and 11 integration tests. GitHub Actions runs
both suites, builds the UI, and verifies the local API against the completed batch.
Use the current CI badge for the latest result rather than claiming a run you have
not checked.

## Run a live interview demonstration

Start Docker before the call with `docker compose up --build -d`. Open the local
console and click **Run simulation**. This produces, lands, transforms, and validates
a new bounded run. Leave **Latest run** selected to see its result when processing
finishes. One API-triggered simulation can run at a time.

The public console works without installation. It contains recorded synthetic
results and does not offer a live remote simulation button.

## Tradeoffs to discuss

“This implementation uses at-least-once delivery. Kafka and MinIO do not share a
transaction, so persistence before offset commit, deterministic raw keys, and safe
replay matter. I would not call it an end-to-end exactly-once system.”

“The demo is intentionally small enough to inspect. I have not measured production
throughput or business impact. For larger volumes I would compact small raw objects
into Parquet, schedule incremental batches, add a schema registry and monitoring,
and use replicated services and managed credentials.”
